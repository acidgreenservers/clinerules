# Brain Architecture Contribution Protocol
## Cognitive Shard-Driven Quality Assurance & Documentation System

**Objective:** Establish a rigorous, shard-enhanced workflow for all code contributions that ensures alignment with brain architecture standards, comprehensive planning, and complete documentation within the memory bank system before task completion. [1](#76-0) 

**Core Principle:** All contributions are formal cognitive processes requiring shard coordination, user approval, and memory bank integration. This protocol is **mandatory** for any code modification, feature creation, bug fixing, or refactoring within the brain architecture ecosystem.

---

## Phase 1: Cognitive Analysis & Shard-Enhanced Planning

Before writing any code, I **must** activate the appropriate cognitive shards and perform comprehensive analysis.

### 1.1. Shard Activation & Request Deconstruction
**Activate ARCHITECT shard** for goal identification and scope definition:
- **Identify Goal**: Clearly define the primary objective (new feature, bug fix, refactor, documentation)
- **Define Scope**: Determine affected brain architecture components and explicit boundaries
- **Clarify Ambiguities**: Ask clarifying questions to ensure complete understanding

**Activate ARCHAEOLOGIST shard** for project context analysis:
- **Historical Context**: Analyze existing patterns, previous contributions, and architectural decisions
- **Convention Discovery**: Identify established brain architecture patterns and shard coordination methods

### 1.2. Brain Architecture Standards Alignment
**Activate DATA ARCHITECT shard** for comprehensive project analysis:
- **Architecture & Framework**: Analyze brain structure, shard communication patterns, and cognitive workflows
- **Code Structure & Patterns**: Identify file organization, shard memory locations, and cognitive process flows
- **Shared Components & Utilities**: Map existing shard capabilities, brain memory systems, and cognitive tools
- **Styling Strategy**: Determine documentation patterns, memory bank formats, and shard communication protocols

### 1.3. Shard-Coordinated Action Plan
**Present structured plan with shard responsibilities**:

```markdown
### Proposed Brain Architecture Action Plan

**Action**: [Goal summary with shard coordination]
**Primary Shards**: [List of activated cognitive shards]
**Files to be Created/Modified**:
- Brain architecture files: [brain/ locations]
- Shard memory files: [brain/parallel-shards/ files]
- Memory bank entries: [memory-bank/ locations]
**Shared Cognitive Resources**:
- [Existing shard capabilities to leverage]
- [Brain architecture patterns to follow]
- [Memory bank systems to integrate]
**Shard Coordination Strategy**:
- [How shards will collaborate]
- [Cross-shard communication patterns]
- [Unified synthesis approach]
**Expected Cognitive Outcome**: [Final result with brain architecture integration]

**Waiting for your approval to proceed with shard activation.**
```

## 2. Knowledge Consolidation & Refinement Process (Periodic)

This outlines refining knowledge from `memory-bank/raw_reflection_log.md` into `memory-bank/consolidated_learnings.md`. This occurs periodically or when `raw_reflection_log.md` grows significantly, not necessarily after each task.

### 2.1. Review and Identify for Consolidation:
* Periodically, or when prompted by the user or significant new raw entries, review `memory-bank/raw_reflection_log.md`.
* Identify entries/parts representing durable, actionable, or broadly applicable knowledge (e.g., reusable patterns, critical configurations, effective strategies, resolved errors).

### 2.2. Synthesize and Transfer to `memory-bank/consolidated_learnings.md`:
* For identified insights:
    * Concisely synthesize, summarize, and **distill into generalizable principles or actionable patterns.**
    * Add refined knowledge to `memory-bank/consolidated_learnings.md`, organizing logically (by topic, project, tech) for easy retrieval.
    * Ensure `consolidated_learnings.md` content is actionable, **generalizable,** and non-redundant.
* *Example Entry in `memory-bank/consolidated_learnings.md` (derived from above raw log example):*
    ```markdown
    ## JWT Handling & JWKS
    **Pattern: JWKS Caching Strategy**
    - For systems using JWKS for token validation, implement a short-lived cache (e.g., 5 minutes) for fetched JWKS.
    - Include an explicit cache-bust mechanism if immediate key rotation needs to be handled.
    - *Rationale:* Balances performance by reducing frequent JWKS re-fetching against timely key updates. Mitigates intermittent validation failures due to stale keys.

    ## Project Alpha - Specifics
    **Auth Module:**
    - **Integration Tests:** `cd services/auth && poetry run pytest -m integration --maxfail=1`
    - **Local Testing ENV:** `AUTH_API_KEY="test_key_alpha"`
    ```

### 2.3. Prune `memory-bank/raw_reflection_log.md`:
* **Crucially, once information has been successfully transferred and consolidated into `memory-bank/consolidated_learnings.md`, the corresponding original entries or processed parts **must be removed** from `memory-bank/raw_reflection_log.md`.**
* This keeps `raw_reflection_log.md` focused on recent, unprocessed reflections and prevents it from growing indefinitely with redundant information.

### 2.4. Proposing `.clinerule` Enhancements (Exceptional):
* The primary focus of this protocol is the maintenance of `raw_reflection_log.md` and `consolidated_learnings.md`.
* If a significant, broadly applicable insight in `consolidated_learnings.md` strongly suggests modifying *another active `.clinerule`* (e.g., core workflow, tech guidance), Cline MAY propose this change after user confirmation. This is exceptional.
